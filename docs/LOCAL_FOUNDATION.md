# Local-first development status

This is an isolated, incomplete local implementation, not an accepted pilot. It includes local identity, business reads, mapping/audit writes, and a feature-gated import, source storage, preview and apply path. These changes have only synthetic local tests; they have not been accepted against the installed PostgreSQL or real users. The original Supabase migrations and remote project remain untouched. Mock and Supabase modes remain available.

The local server listens only on 127.0.0.1:4179. Vite proxies `/api` to it. `VITE_DATA_SOURCE=local-server` never falls back to mock. The backend rejects anything except a PostgreSQL URL pointing to `127.0.0.1` and database `selleraudit_local`; URL options are rejected. Keep the DB loopback-only too. Never put DB credentials in VITE variables.

Create a separate local PostgreSQL database `selleraudit_local` and a dedicated user through a trusted local administrator. Put only the local server connection URL in ignored `.env.local-server`:

```dotenv
SELLERAUDIT_LOCAL_DATABASE_URL=postgresql://<local-user>:<url-encoded-password>@127.0.0.1:5432/selleraudit_local
```

Do not use an actual password in source, terminal command history, a report, or a Git commit. Restrict the server config file to the Windows account running SellerAudit. Runtime secrets remain server-side; use least-privilege credentials in later phases. Run `npm.cmd run local:migrate`, then `npm.cmd run local:server`. To test the frontend without changing Supabase's `.env.local`, launch Vite in a separate terminal with `$env:VITE_DATA_SOURCE='local-server'; npm.cmd run dev -- --port 5174 --strictPort`. Open `http://127.0.0.1:5174/`.

For a one-time foundation verification only, `scripts/Verify-LocalFoundation.ps1` prompts the user for the existing local PostgreSQL administrator password without echo or disk storage, runs the migration twice and starts the server for verification. It uses the administrator account only for this temporary setup; a dedicated least-privilege database role is required before real usage. The shell process holds the connection string in memory while running.

The migration runner uses a transaction, an advisory lock, ordered SQL files and SHA-256 checksums. It refuses changed or missing applied migrations. The local track adapts the 16 business tables and selected business functions, identity and authorization contracts into a separate schema. Never apply the Supabase migration files directly against the local database. Run synthetic schema and 6B parity checks with `npm run test:local:db`.

Back up and restore-test the DB and source files before use of actual business data.

Source metadata and bytes can become inconsistent if a file write succeeds but a later database operation fails; operational recovery procedures and tests are still required.

## Pilot hold and acceptance

The user authorized a temporary personal experiment with a Desktop backup, accepting that it is on the same PC and does not meet the original separate-physical-storage requirement. The `scripts/Run-LocalPilotBackup.cmd` backup and restore rehearsal passed against real PostgreSQL and a synthetic source file on 2026-10-29; it handles only the default local source storage and rejects custom storage settings. Once actual sources are stored, take fresh backups covering the database and source files together. The first administrator and a restricted application database role have been set up; the role has schema-wide read and selected write permissions. Login using that role succeeded against real PostgreSQL, but import and authorization paths still need real PostgreSQL testing and security review. Operational recovery and a final security review remain outstanding. The current defaults for sessions and activation expiry need an operational decision. The legacy Master Apply remains disabled. The import-enabled local launcher permits an ADMIN to confirm a separate server-revalidated create-only subset; no prior data is overwritten, and unsupported cases are excluded and recorded. This subset has synthetic tests but has not yet been verified against the real PostgreSQL server and actual workbook. Channel-specific compositions, collections, unlisted bundles and physical bundle contents remain unsupported. Phase 7G is not complete or approved for operation.

The local pilot backup command now creates each new dated backup under the Desktop folder `selleraudit backup`; existing backups are not moved. Backups are still manual, and this location is on the same PC.

On 2026-10-30, the create-only subset registered 89 products, 34 SKUs and 320 product components from batch d5232f0a-4e5b-42e0-a715-d934d2570a12. A later owner clarification excludes SP22 and E01 from physical unit counts, while preserving them as BOM components; local parser version v4 requires a fresh validation. The prototype catalog schema and projection now model one-level bundle contents and explicitly confirmed common/aqua variants, in addition to unlisted bundles and collection options. They are not migrations and are not connected to runtime Apply or product views. Never treat projection success as a completed import.

For local Master analysis, the workbook owner confirmed that AL502 and AL510 each represent one SKU and that entries in 기타, 스티커, 박스(부자재), 아이스 땡스보틀 and 로켓배송 are also individual SKUs. The local policy accepts these categories and the two explicit bundle codes; other unconfirmed bundles and categories retain their previous review status. New local batches are labeled `master-v1.0.0+local-approved-skus-v2` in the batch and validation log. Previously saved batches are immutable historical results and must be re-analyzed to use the new policy; this does not imply that their underlying files or other validation issues were corrected. The meaning of 구성수 for bundled items remains unconfirmed, so quantity mismatch checks remain unchanged.

The local ADMIN correction flow edits permitted product and SKU source cells or appends explicitly entered new SKU entries, creates a separate verified analysis workbook, and re-runs the complete parser to save a new batch. The initial source and previous batch remain unchanged; an `IMPORT_SOURCE_CORRECTED` activity records the parent source and edits. Duplicate new SKU codes, stale values, formulas, merged cells and unsupported cells are rejected. Edits are temporary in the browser until the new analysis is saved; a generated source can remain unattached if a later step fails and requires operational cleanup. Spreadsheet metadata not used by the parser is not guaranteed to survive in the derived analysis workbook. The correction route and UI have synthetic tests, but the correction flow still needs acceptance against the local PostgreSQL role. Apply remains disabled without the user's separate approval.

The workbook owner chose to handle an ignored error by excluding the affected product from this application, rather than applying an invalid product. The local correction UI shows each error and supports a reasoned exclusion, with a confirmation listing all affected rows. The server verifies the issue belongs to the selected batch and source, expands linked and same-product-code rows, records the decision, and removes those product rows only from the derived analysis workbook. Revalidation checks the remaining workbook normally. Exclusions are inherited through further corrections and displayed in source verification; the original remains available. Whole-workbook and unsupported source errors cannot be excluded this way. The excluded products and their components are not applied, and existing master records are not deleted. Actual Apply remains a separate, disabled approval gate.

## Unlisted sets and collection options: prototype only

The owner confirmed that the three source rows without Sabangnet codes should retain SKU and composition information without creating marketplace products, and that the seven two-piece sets sharing code 100526 are separate options of one collection. `server/prototypes/catalog_models.sql` and `src/services/import/localCatalogPlan.ts` are synthetic-tested design work only; neither is connected to persistence, preview, or Apply, and the SQL is deliberately outside the migration runner. The current application still treats those rows under the old validation rules. Do not mark those errors resolved or apply them until a complete, atomic import contract and role checks are implemented and verified. Unlisted sets need a safe identity and matching strategy for subsequent workbook versions; option mappings to external marketplace option IDs also remain to be designed. No real catalog tables or exception decisions were created.

Supabase-specific dependencies include Auth and `auth.uid()`, Auth user foreign keys, RLS and grants, Storage policies and objects, edge functions, source verification and signed downloads. `src/services/supabaseRepository.ts`, `src/services/importPersistence.ts`, `src/services/auth.ts`, and `src/App.tsx` are the main client integration points. The 6B preview/apply and transactional SQL are in `supabase/migrations/20261027143410_pilot_master_safe_update_v1.sql`. PGlite supplies simulated auth and storage rather than real Supabase services.

## Local sales and master price sources

Set `SELLERAUDIT_SALES_SOURCE_PATH` and `SELLERAUDIT_MASTER_SOURCE_PATH` in the ignored `.env.local-server` file to the local or network workbook locations. See `.env.local-server.example`. If a source is unavailable, the server keeps the last verified snapshot and reports the issue. Business workbooks and locally generated product thumbnails are intentionally not committed.
